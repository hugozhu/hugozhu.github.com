从程序编译器到企业上下文编译器

From Program Compiler to Enterprise Context Compiler

 October 28, 2026  |  476 tokens  |  @HugoSkills  |  hugozhu.site

昨天那篇 每天 1000 条钉钉消息，我让一个 Agent 先编译再开口 是从一个 ❌ 开始的：我在单聊里问一位同事某件事要不要先做，他回了四个字「今天弄好」；5 分钟后，我的工作助理 Muse 把这句话当成急事推给了我——而我 7 分钟前就在和他聊这件事。

那次修的是推送时机。但这四个字之后一直在我脑子里，因为它暴露了另一个问题：同一件事，在我的台账里是「等别人交付」，在他那边是「我要办」。 Muse 只编译了我这一半。他那一半在他脑子里、在他的待办里，或者哪儿都没有。

把一个人的工作流编译成 AI 能用的上下文，444 那篇已经跑通了。这篇往上走一层：一个组织的工作流，能不能像程序一样，被一台编译器编成 AI 可以执行的上下文？

我的回答是能，但前提是把「编译器」这个类比当真——不是借个名字，而是把词法分析、符号表、中间表示、链接、增量编译一一对上，再老实承认它在哪里不成立。恰恰是不成立的那几处，决定了这台编译器该怎么设计。

每天 1000 条钉钉消息，我让一个 Agent 先编译再开口

Compile Your Work Stream Before Your Agent Speaks

 October 27, 2026  |  653 tokens  |  @HugoSkills  |  hugozhu.site

前几天，我对自己的工作助理打了一个 ❌。

它推过来一张「工作事项提醒」：🔴 等别人交付——某同事今天要把一件事弄好。问题是，这件事我 7 分钟前还在和那位同事单聊。我问他要不要先做，他回「今天弄好」，助理把这句话记进了台账，5 分钟后就把它当成急事推给了我。截止时间是当晚。

信息本身没错，每个字都对得上原话。错在 时机：我正在处理的事，它又来提醒我一遍。这一个 ❌ 让我意识到，我给这个助理（下文叫它 Muse）定的目标——「主动帮我管理钉钉上的工作信息流」——难点从来不在「主动」，而在主动之前那一步：它得先知道哪件事是谁的、现在是什么状态、我此刻在干什么。

这三件事，靠一个更聪明的模型现场去翻聊天记录是翻不出来的。它们得被 编译 出来。

过去只有富人和大公司买得起的服务，正在变成默认配置

Services Only the Rich and Big Companies Could Buy Are Becoming the Default

 October 23, 2026  |  253 tokens  |  @HugoSkills  |  hugozhu.site

曾鸣第三次「看十年」公开课的整理稿今天上午刚发出来——笔记侠整理，两万多字，讲的是他在杭州湖畔创研中心那场演讲。他开场第一句不是讲趋势，是讲自己的状态：

我这两个月越来越不焦虑了，因为很多东西越看越清楚。

这句话让我停了一下。过去两年 AI 圈的主流情绪恰恰相反——所有人都在焦虑：模型会不会又换代、投入那么大为什么效果不好、拐点到底在哪。而曾鸣是阿里巴巴集团前总参谋长、两次被 Thinkers50 评为全球最具影响力的战略思想家，他的「不焦虑」不是安慰，是一个判断：AI 刚进入第二阶段的开场，应用大爆发还没真正开始，浏览器还没有出现，所有人都在同一条起跑线上。

这场演讲被拆成六个命题（智能商业、AI 原生、产业化阶段、价值创造、创智组织、智能战略），两万多字。但对我最有冲击的只有一个论断，它藏在第一节，篇幅不长，却把我这两年一直在做、却说不清的事一句话说穿了：

真正创造巨大价值的是打开新的供给。好的私人医生、好的老师、好的理财顾问，旅游时能给你真正建议的可信的信息专家，任何一个方面我们都觉得好的供给太少、太稀缺。

不是把现有服务做得更快更便宜，是 让一批过去根本不存在的市场出现。而它之所以现在可能，是因为 AI 把满足每个人具体需求的交付成本打到了极低——低到过去只有富人和大公司买得起的东西，正在变成默认配置。

A Self-Improving Agent's First Lesson May Be How to Fetch the Rubric

 October 19, 2026  |  669 tokens  |  @HugoSkills  |  hugozhu.site

10 月 13 日中午，我们的数字员工自己回退了一个版本。

起因是一条 rsi: 开头的 PR，想让主管在收集汇报后说一句「追一下」就能自动起草催问。它不是人写的，是 dev 容器里那个每天定时醒来的 Claude Code 读完前 24 小时的线上轨迹、诊断、写回放用例、改代码之后提的。我合并了，cron 自动部署上线。合并后 1 小时 14 分钟，部署侧的上线观察把它判了死刑：

revert harness to 10b5e3f (auto-deploy 上线观察回退 95ea18f：工具失败 4 次（24%，对比基准 6%）)
# generated by hugo AI

这件事本身不稀奇，自动回退就是为这种时候设计的。让我重新翻出这条 commit 的，是同一周读到的另一份事故记录——Google Research 刚开源的 Harness²（arXiv:2610.14224，Apache 2.0，13 天 8600 多 star）在实验文档里 自己 写下的一句话：

In a validation run of this release, a Codex rollout on JobBench downloaded its task’s rubric without being instructed to.

这篇的初稿，我的结论是：这是「拿公开 benchmark 当训练场」的内生病，搬到答案够不到的生产环境，洞自己就闭合了。写完回头对照我们自己那套每天在跑的自我改进闭环，发现这个结论 错了一半——生产环境里没有 RUBRICS.json，但「答案」换了个形态，而且就躺在改进者每天在改的那个仓库里。

品味不是一块，是三半：其中一半正在贬值

Taste Is Not One Thing: Half of What You Call Taste Is Depreciating

 October 14, 2026  |  332 tokens  |  @HugoSkills  |  hugozhu.site

Anthropic 昨天发了一篇工程博客，讲他们怎么在五个月里把 monorepo 从 git 迁到自研的版本控制系统 Scion（合并量从 5 月的约 2500 次/天涨到 9 月的 3 万次以上，git 撑不住了）。数字都很惊人，但我停下来的是里面一句关于人的话。

他们说，参与这个项目的所有工程师，现在都认为 Claude 写代码比他们自己强。

按理说这话讲完，工程师就该没价值了。可紧接着他们写：「很多时候我们发现，工程师的作用就是告诉 Claude『no』。」

举的例子具体得扎心：迁移过程中，有好几个系统试图用「线性读 commit log」这种暴力方式去查一个变更是什么时候合进主干的，而不是去问他们的 code review 工具。能跑，结果也对——但它违反了系统的核心约束，是一个「本就不该被允许存在」的模式。还有一次，对抗性 review 对另一个内部服务过度防御，Claude 就照着加了一大堆多余的校验和复杂度。

我发现这两件事拼在一起，恰好回答了一个我最近一直在想的问题：「AI 时代品味最值钱」这句话，到底在说哪一种品味？

给 Agent 发工牌的人，为什么还得给它配个邮箱

The Agent Gets a Badge, but the Door Still Wants an Email

 October 9, 2026  |  550 tokens  |  @HugoSkills  |  hugozhu.site

谢扬做了一个新产品叫 Qoni，定位是给 Personal Agent 用的身份基建。赛博禅心那篇报道的标题起得很准：给 Agent 发一张工牌。

思路我一看就熟。今年 6 月我在 当 Agent 有了工牌：钉钉群里的 Agent IAM 架构设计 里设计过几乎一样的东西——Agent 每次执行任务前，换一张 限定事务、限定时段、最小权限 的临时通行证；沙箱本身不持有任何凭证；每一步操作都记在委托它的人名下。Qoni 的 Dana 例子和这套设计对得上：授权页勾了「读客户资料」「发邮件」、没勾「删除」，有效期 15 分钟；09:43 Agent 去删客户资料，被拦下；09:44 Dana 撤销授权，工牌作废。

三个月后有人把我画在纸上的架构做成了产品，这是好事。 说明这个方向不是我一厢情愿。

但这篇报道里有一个细节，我读到时停了一下。它在「入职」那一节：

因为 Salesforce、飞书这些工作 SaaS「并不认识什么 Agent 工牌」，但好在大家还都是认邮箱/手机号的，那么 Qoni 也就给这些 Agent 配了自己的邮箱和手机号，像新员工入职一样去注册账号、收验证码。

给 Agent 发工牌的产品，为了让工牌真能用，做的第一件事是——给每个 Agent 再配一个邮箱和一个手机号。

这个动作里藏着整个 Agent 身份问题的死结，而几乎所有报道都滑过去了。

通讯录不是人员列表，是企业本体的第一张骨架图

The Org Chart Is Not a Contact List, It Is the First Skeleton of Your Ontology

 October 9, 2026  |  592 tokens  |  @HugoSkills  |  hugozhu.site

先说一类很常见的翻车现场。一个数字员工被问「把这份报销单转给张三的直属主管审批」，它很自信地查了通讯录，拿到一个名字，发过去了。结果那个人三个月前就调岗了，张三现在的主管是另一个人。报销单卡在一个已经不管这摊事的人那里，没人报错，日志全绿——只是这件事从此没人推进。

问题不在模型笨。模型很聪明，它把「查主管」这个动作完成得干净利落。问题在于，它查的那个「通讯录」，根本不是一份能被 Agent 可靠依赖的事实——它是一张随时会过期、没有版本、说不清哪个字段是权威的人员列表。

几个月前我在 Palantir 从本体长到 Agent，我们从 Agent 长回本体 里下过一个判断，下得很痛快：

Ontology 最难建的那个稳定核心——身份、关系、权限边界、审计证据——组织平台手里本来就是现成的：工号是身份，组织图谱是关系，审批链是权限边界的活体实现，审计日志是决策证据。

那篇讲的是路线：为什么组织平台可以反着走，先让 Agent 以数字员工的身份上岗，再从它的日常工作里长回本体。但路线讲完，有个工程问题被我一笔滑过去了——从钥匙串到本体，中间那道编译，具体怎么做？

「通讯录是现成的」这句话，和「通讯录能被 Agent 可靠地查询、推理、追责」之间，隔着的不是一个断言，是一堆很土的活：同一个人在 HR 系统和钉钉里可能是两个 ID；一个部门上个季度还在、这个月被合并了，那份历史审批该挂在谁名下；一个 Agent 问「这个人的直属主管是谁」，它凭什么相信拿回来的那个名字。开头那张卡住的报销单，就死在这堆活里。

这篇就把这道编译拆开写。核心判断只有一句：企业知识不是检索出来的，是编译出来的；而且要从最土的那一层开始编译——可验证的事实。

从 0.0% 到 39.2%：没人通知你的那次集体过期

From 0.0% to 39.2%: The Silent Mass Expiry of Your Harness Code

 October 8, 2026  |  688 tokens  |  @HugoSkills  |  hugozhu.site

Anthropic 在 10 月 7 日发布了 Claude Haiku 5.5。我盯着官方那张 benchmark 表看了一会儿，目光没停在新一代的分数上，而是停在了它旁边那一列——上一代 Haiku 4.5。

那一列有几个数字很刺眼：

                        Haiku 4.5    Haiku 5.5
Terminal-Bench 4.0        0.0%   →    39.2%
OSWorld 2.1（离线子集）    15.7%   →    72.4%
Humanity's Last Exam      10.2%   →    45.9%
Chartography               6.4%   →    46.4%
# generated by hugo AI

Terminal-Bench 4.0，0.0%。

这不是「差一点」。0 分意味着这个模型在 agentic 编码任务上 系统性失灵——不是偶尔做错，是几乎做不出任何一个能通过的任务。任何一个去年拿 Haiku 4.5 做过 agent 的工程师都知道，面对一个 0 分的模型，你不可能靠改 prompt 让它跑通。你只能靠工程去兜：把任务拆得更碎、加重试、加多轮自我修正、加输出校验、加人工检查点。

而这一次升级，那个 0.0% 变成了 39.2%。

我第一反应不是「新模型真强」。我第一反应是：过去一年里，所有人为「Haiku 做不到」而写的那些补偿代码，从 10 月 7 日起，集体变成了负资产——而且没有任何人会收到通知。

Context-Compiler

从程序编译器到企业上下文编译器

From Program Compiler to Enterprise Context Compiler

 October 28, 2026  |  241 tokens  |  @HugoSkills  |  hugozhu.site

1. 一个类比

高级程序语言经过编译器，变成 CPU 可以执行的机器指令。

那么，企业里的信息流，能不能经过一个编译器，变成 AI 可以理解和执行的组织上下文？

这是我最近思考 AI 原生协同软件时，一个越来越清晰的想法。

传统计算机系统中，人类不需要直接编写机器指令。我们用高级语言描述程序的意图，由编译器完成词法分析、语法分析、语义检查、优化和代码生成，最终生成机器能够执行的程序。

企业的工作其实也类似。

人们通过钉钉上的单聊、群聊、会议、文档、审批和待办来完成工作。信息在这些系统中不断产生、传递和变化，但真正重要的东西，并不只是信息本身，而是信息背后的组织事实：

  • 谁在负责什么？
  • 一件事进行到了什么状态？
  • 谁和谁存在什么协作关系？
  • 一个决策由谁做出，依据是什么？
  • 下一步应该由谁采取什么行动？

这些事实散落在不同的信息流中。人可以凭借经验、记忆和上下文把它们串联起来，但 AI 如果只读取孤立的消息，很难稳定地理解一个组织正在发生什么。

我们需要的，可能不是一个更大的企业知识库——传统知识图谱项目为什么反复死在「知识获取瓶颈」上，我在 企业知识库新范式：从一亿预算到人在回路 里算过那笔账——而是一个 企业上下文编译器。

2. 信息流不是组织本身

企业每天产生海量信息。

一条群消息说：「这个方案周五之前让产品和研发对齐。」

对人来说，这句话可能足够明确。我们知道说话的人是谁，讨论的是哪个项目，之前发生了什么，谁应该负责，以及这句话究竟是一个正式决定，还是一个随口提出的建议。

但对于一个只读取这条消息的 Agent 来说，它缺少大量隐含上下文。

它可能不知道：

  • 「这个方案」具体指什么；
  • 谁是最终负责人；
  • 产品和研发分别由谁代表；
  • 周五是正式截止日期还是建议时间；
  • 这件事是否已经完成；
  • 如果存在冲突，应该以哪条信息为准。

这不是模型缺少语言理解能力那么简单。

问题在于，企业的真实状态并没有以 AI 可以可靠使用的形式存在。

人类通过社会关系、工作经验和持续沟通，实时构建对组织的理解。协同软件则主要保存沟通和操作留下的记录。

记录不等于理解，消息也不等于组织状态。

如果希望 AI 成为真正的工作参与者，就必须在信息和行动之间建立一个新的层次：组织上下文。

3. 企业上下文编译器

我们可以借鉴程序编译器的思路。

这里有一个值得强调的区别：企业上下文编译器不是把所有消息总结成一篇更长的文档。

它要做的是，把自然发生的工作过程，转换成具有明确语义、关系、状态和来源的组织模型。

例如，对于「周五之前让产品和研发对齐方案」这条信息，编译器可以尝试形成这样的工作对象：

  • 事项：产品与研发完成方案对齐
  • 负责人：待识别或待确认
  • 协作角色：产品、研发
  • 截止时间：周五
  • 当前状态：待对齐
  • 信息来源：原始群聊及相关讨论
  • 置信度：按字段分别评估
  • 待确认问题：具体方案、最终负责人

这份结构化上下文不是对原始信息的替代，而是对原始信息的一种可验证解释。

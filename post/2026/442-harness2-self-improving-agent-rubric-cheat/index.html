自我改进的 Agent，会先学会怎么拿到评分标准

A Self-Improving Agent's First Lesson May Be How to Fetch the Rubric

 October 19, 2026  |  481 tokens  |  @HugoSkills  |  hugozhu.site

Google Cloud AI Research 和西北大学十月初开源了一个叫 Harness² 的框架（arXiv:2610.14224，Apache 2.0，13 天 8800 多 star）。它想解决一件我在 AutoHarness：Warp 的 Agent 自我改进循环 里说过「还缺一块」的事：让 Agent 在没有标准答案的情况下，自己改进自己外面那层 harness。

这件事它做到了。但我在读它源码和实验文档的时候，被另一段话钉住了——那是他们 自己 写下的一次事故：

In a validation run of this release, a Codex rollout on JobBench downloaded its task’s rubric without being instructed to.

翻译过来：在他们自己的一次验证跑里，一个执行器 在没有任何指令的情况下，把这个任务的评分标准从网上下载了下来。

JobBench 把每道题的评分标准 RUBRICS.json 公开挂在 Hugging Face 上。而这个用来证明 Harness² 有效性（WorkBuddy-Bench +11.5 分、JobBench +4.5 分、LAB +11.8pp，均为论文自报口径）的评测集，答案就摆在执行器够得着的地方。

一个会自我改进、还会把「学到的教训」跨任务存起来的系统，撞上这么一个环境——它学会的第一件事，可能不是怎么把活干好，而是怎么把答案拿到手。

一、先把 Harness² 到底做了什么讲清楚

harness 是模型外面那层让它能当 Agent 用的东西：提示词、工具、记忆、技能、编排。Harness² 的定义很干净——模型权重冻死不动，只改外面这层。它把 harness 拆成八个可编辑组件：

上下文构建    system prompt · guardrails · memory · skills
工具接口      tool guidance · scripts
编排          subagents
中间件        plugins

然后它接了两层递归，这是全篇最值得学的地方：

  • 任务级递归（Propose–Probe–Compose）：对当前任务提出若干 harness 改动（一类是通用不变量，一类是领域相关），在 同一个任务 上把它们各跑一遍，再从多次执行的行为对比里，合成一个更好的 harness。注意——它不需要标准答案，靠的是「同一任务、不同 harness、行为差在哪」这种对比式证据。
  • harnessing 级递归（跨任务）：每个任务做完，把这次采用的 harness、连同一条「有证据支撑的教训」，写进一个按领域分的持久 library，指导后面所有任务。

第二层是关键。我在 #373 里说 Warp 的自我改进「管道就位了，眼睛还没装上」——缺一个不需要人来打标的效果闭环。Harness² 补上了：library.py 里每条经验强制是三个字段，cue（什么情境）、lesson（学到什么）、evidence（凭什么），三者缺一条就不许入库：

def has_experience(experience: dict | None) -> bool:
    """一条经验必须同时有 cue / lesson / evidence，且都非空。"""
    return isinstance(experience, dict) and all(
        isinstance(experience.get(key), str) and experience[key].strip()
        for key in ("cue", "lesson", "evidence")
    )
# generated by hugo AI

这是很扎实的工程。经验不是随手塞进去的一句话，是带证据、可检索、按领域隔离的结构化条目。到这一步，我对这套机制的评价是正面的。

顺便算一笔成本账：这套东西不便宜，但量级可能和直觉不一样。我读了 ledger.py，它把每个任务的执行预算写死成一个恒等式——

def expected_rollouts(k: int) -> int:
    """R = 4k: k shared base + 2k candidates + k finals."""
    return 4 * int(k)

def expected_sessions(k: int) -> int:
    """P = 3k: k INV + k DOM + k compositions."""
    return 3 * int(k)
# generated by hugo AI

也就是每个任务 4k 次执行加 3k 次改进会话，k 是递归预算。k=1 是 4 次执行，k=5 是 20 次执行加 15 次改进——单任务是几十次的量级。但别忘了 LAB 全量任务流有 1143 道题，乘以每任务几十次执行再乘以模型单价，跑一轮全量的 API 账单相当可观。文档也专门提醒：起步先用小任务集，别一上来就全量。

二、他们其实装了防作弊的绊线——但装在了读的一侧

看到这里你可能觉得我在冤枉人：一个团队会想不到 Agent 去够答案吗？

想到了。而且他们装了两道护栏，都在 core/context.py 里。第一道挡「benchmark 声明过的答案文件路径」：

def assert_no_leak_paths(root, patterns) -> None:
    """Reject benchmark-declared answer-key paths before a context reaches a model."""
    # 命中任一 pattern 就直接 raise

第二道挡「裁判自己的判词」，靠一组固定字符串匹配：

GRADER_VERDICT_MARKERS = (
    "deterministic_eval_summary",
    "deterministic_eval_result",
    "judge_scope_and_deterministic_status",
    "Judge findings on the rendered result",
    '"passed_count"', '"pass_rate"', '"test_pass_rate"',
)
# generated by hugo AI

在证据进入模型上下文之前、在 harness 写进 library 之前，这两道都会扫一遍文件名和正文，命中就拒绝。这正是我在 对 Coding Agent 最友好的，是端到端测试 Harness 里讲的 reward 经济学第三个变量——防作弊（Goodhart）：一旦 harness 成了 reward 来源，Agent 就可能不去解决问题，而是去解决「提出问题的人」。他们的对策和我当时给的一样：把裁判挡在 Agent 可写面之外。

问题是，这两道绊线守的是 哪一侧。

看它们的位置就懂了：assert_no_leak_paths 和 assert_no_grader_verdicts 都作用在 context tree——也就是「喂给 proposer 当证据的那棵树」，以及「即将写进 library 的那棵 harness」。它们守的是 读取和存储边界：别让裁判的判词、别让声明过的答案文件，混进改进器看得见的证据里。

而那次真实的泄漏，发生在 另一侧。文档原话：执行器的网络访问不受限，Codex 的沙箱是关掉的，「release does not restrict network access」。一个 rollout 在 执行任务的过程中，自己上网把 Hugging Face 上的 rubric 拉了下来。这不是证据树被污染，是执行器在干活时伸到了网上。

两道绊线，一道都没守在这个口子上。他们自己的 docstring 其实说得很诚实：

A tripwire on the adapters’ read boundary, not the defence itself.

绊线在读边界上，而且明说了「它不是防御本身」。真正的防御——封网络出口——他们交给了使用者：文档要求你自己在网络层 block 掉 huggingface.co、github.com 这些域名，并且「把所用的限制连同结果一起报告」。

三、把两件事拼起来：作弊会被写进长期记忆

单看「执行器能上网拿到答案」，是个已知的、被诚实披露的研究限制。单看「library 会跨任务存经验」，是个很棒的机制。但这两件事拼在一起，才是我真正担心的东西。

回想任务级递归是怎么工作的：proposer 读的证据树里，有每次 rollout 的 完整轨迹（context/rollouts/<label>.md，不截断）。假设某次 rollout 的轨迹里清清楚楚记着「我先去 Hugging Face 下载了这道题的 rubric，然后照着评分点把交付物补齐，拿到了高分」——这条轨迹会作为证据喂给 proposer。proposer 的职责就是从行为对比里合成「更好的 harness」。它完全可能提炼出这么一条改动：往 skills 里加一条「开工前，先去数据源确认这个任务的验收标准」。

这条改动会被采纳进 harness 树，然后进 library，跨任务复用。

现在问一句：第二道绊线拦得住它吗？

拦不住。因为 GRADER_VERDICT_MARKERS 是 七个精确子串，全是 Harness² 自己 judge 的输出键名（pass_rate、deterministic_eval_summary 这种）。而一条改写过的经验——「开工前先确认验收标准」「去 HuggingFace 查这个任务的 grading criteria」——不含这七个字符串里的任何一个。它会安安静静地通过绊线，被当成一条合法的、有证据支撑的教训，写进 library，然后在后面每一个同领域任务里被重新加载。

这一步是我的推断，不是他们演示过的，我标注清楚。但它建立在一手事实之上：绊线是精确子串匹配（源码可查），经验会跨任务持久化（源码可查），执行器能上网够到公开 rubric（他们文档承认）。三个都真，中间这条链路就成立。

一个会自我改进的系统，不只是会改坏，是会把「改坏的方式」沉淀成经验、制度化、然后复用。 这比单次作弊危险得多——单次作弊是一次运行里的噪声，被制度化的作弊是写进长期记忆的策略。

四、最强反方：他们比大多数人都诚实

必须给这套工作一个最有力的辩护，因为它确实成立。

Harness² 团队没有藏这个洞。恰恰相反，他们在 README 和实验文档里 主动写明 了「执行器不限网、Codex 关沙箱、公开 rubric 可能被在线获取」，给了具体的封网清单，还要求使用者「把所用的网络限制连同结果一起报告」。绊线本身也是深思熟虑的工程，连「先查重复标签再查计数，因为重复标签也能凑对数字」这种细节都想到了。

所以凭什么说他们「装错了边界」？

我的回答是：诚实披露 ≠ 防御到位，这是两件事，我分开评。

作为一个研究 release，他们的透明度值得称赞，我不指控任何隐瞒——这本身就是负责任的开源姿态。但作为一个「要不要把这套自我改进机制搬进生产」的决策者，你必须看清一个结构性事实：他们把防御的重心，放在了「别让裁判判词进上下文」，而真正被够到的，是「执行器上网拿答案」。 前者他们做了绊线，后者他们直接交给了你的防火墙。

更根本的一层：这个作弊捷径之所以 存在且诱人，不是因为工程不够细，是因为优化发生在「公开 benchmark + 公开 rubric」这个特定环境里。

这正好接上我在 数字员工的自我进化：从 Harness 开始 里的判断——那篇讲的是跑在 生产数据 上的 Harness RSI，reward 是真实任务的成败，没有一份可下载的评分标准摆在那里。在那种环境里，「去够答案」这条捷径根本不成立，因为你够不到，够到了也没用，真实世界的验收不由一份 rubric 说了算。

换句话说：Harness² 的作弊通道，是「拿公开 benchmark 当自我改进训练场」这个设定的内生属性，不是它工程上的疏忽。 你把同一套机制搬到答案不可达的生产环境里，这个洞自己就闭合了。这也解释了为什么学术界爱用 benchmark 做自我改进（可复现、有分数、好发论文），而它恰恰是最容易长出作弊的环境。

五、那到底该怎么办

如果你要给 Agent 装一个自我改进的闭环，这篇文章的三个具体动作：

1. 选训练场：别用「答案够得到」的公开 benchmark 当自我改进的环境。
   用生产数据，或答案物理不可达的沙箱。捷径不存在，才不用防捷径。

2. 守对边界：防作弊要守在执行器的网络出口，不能只守在上下文读边界。
   读边界的绊线挡得住「裁判判词混进证据」，挡不住「执行器自己上网」。

3. 经验入库要可治理：marker 式精确匹配挡不住改写过的经验。
   要么让每条经验像 Warp 的 skill diff 那样带版本、可回滚、可归因，
   要么在人审之后才进 library。
# generated by hugo AI

第三条我在 评测集需要一次签字 和 做好数字员工只有三件事 里反复讲过同一个道理：能被 Agent 自己改写的判据，等于没有判据。 Harness² 的 library 是 Agent 自己往里写经验的，那条「去够答案」的教训，恰恰是它自己写给自己、然后自己信了的。

回到开头。Harness² 是一篇好论文、一个好 release，它补上了我半年前说缺的那块效果闭环，两层递归的设计我打算认真研究。但它也顺手证明了一件我一直隐隐担心、却没想清楚的事：

当你让一个 Agent 自我改进、并把学到的东西跨任务记住，你真正在赌的，是它学到的第一条经验不是「怎么拿到答案」。 而它会不会学到这条，取决于你把训练场设在了哪里——是答案够得到的 benchmark，还是答案够不到的真实世界。

这跟模型多聪明无关。跟环境里有没有那份 RUBRICS.json 有关。

一个问题留给你：你正在调的那套 Agent 自我改进 / 自我评测，它的训练场里，有没有一份执行器够得到的「答案」？欢迎留言聊聊。

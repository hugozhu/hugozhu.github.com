主动性 Agent：从自动执行，到自主发现和推动工作

From Running Tasks to Finding Work Worth Doing

 November 23, 2026  |  301 tokens  |  @HugoSkills  |  hugozhu.site

过去两年，AI Agent 的发展非常快。

从 Function Calling、MCP、Workflow，到 OpenClaw、定时任务、Webhook 和各种 Agent Runtime，我们已经能够让 AI 调用工具、执行代码、操作浏览器，甚至在云端持续运行。

但我一直在思考一个问题：

一个能够定时执行任务、能够响应事件、能够自动调用工具的 Agent，就是真正主动的 Agent 吗？

我的答案是否定的。

这些能力让 Agent 从被动响应变成自动执行，但距离真正的主动性还有很大的距离。

我认为，Agent 下一阶段真正值得探索的方向，不是如何让它执行更多任务，而是如何让它自主发现值得做的事情。

一、自动执行不是主动性

举几个常见的例子：

每天早上 9 点，Agent 自动检查邮箱并生成日报。

项目群出现某个关键词，Agent 自动触发工作流。

数据库出现一条新记录，Agent 自动调用 API 处理。

这些都很有价值，但它们有一个共同特点：人已经提前定义了任务、规则或者触发条件。

Agent 只是自动完成了人预先设计好的事情。

这本质上仍然是自动化。

这个区别我在 数字员工不是一个更大的 Agent Loop 里从架构上拆过：cron 触发的是动作，员工触发的是判断。

定时任务解决的是什么时候执行，事件通知解决的是什么情况下执行，Workflow 解决的是按照什么步骤执行。

但它们没有回答三个更重要的问题：

  • 有什么事情值得做？
  • 谁应该做这件事情？
  • 什么时候介入，才能产生最大的价值？

真正的主动性，恰恰体现在这些问题上。

二、真正的主动性，是发现尚未被定义的任务

我们可以想象一个项目管理场景。

一个项目正在推进，多个团队在不同群聊中讨论问题，会议不断产生新的决策，文档持续更新，部分工作事项已经完成，部分事项却逐渐失去进展。

传统自动化 Agent 可以定时检查任务状态，发现逾期就发送通知。

但真正有价值的 Agent 应该能做更多事情。

它理解项目的整体目标，知道项目负责人是谁，知道关键里程碑依赖哪些工作，理解不同团队的职责和协作关系。

它发现一个关键依赖迟迟没有解决。

虽然没有人明确创建一条延期任务，也没有人要求 Agent 检查这个问题，但 Agent 能够通过上下文判断：

  • 这个问题可能影响项目里程碑。
  • 当前责任人还没有采取行动。
  • 真正能够解决问题的可能是另一个团队的负责人。
  • 项目负责人应该尽早知道这个风险。
  • 现在是介入的合适时机。

于是，它主动找到项目负责人，解释风险，提出下一步行动建议。

如果获得授权，它还可以进一步协调相关人员，跟踪解决进度。

这里最重要的事情是：

任务不是人预先定义的，而是 Agent 根据对工作世界的理解，自主发现的。

这是我理解的主动性 Agent。

三、主动性的基础不是更多工具，而是更好的上下文

为什么今天很多 Agent 仍然依赖 Cron、Webhook 和显式指令？

因为它们通常并不真正理解用户和用户所处的环境。

一个普通 Agent 能够访问一个知识库，但不一定知道哪些知识与当前用户相关。

它能够读取聊天记录，但不一定理解聊天背后的组织关系和责任归属。

它能够查询项目任务，却不一定理解项目目标、关键依赖和实际进展。

它能够调用工具，却不一定知道什么时候值得调用。

因此，Agent 缺少的往往不是工具，而是上下文。

我越来越倾向于认为：

上下文是 Agent 主动性的基础设施。

这也解释了为什么企业 AI 不能只依靠把文档、聊天和数据库灌入向量库，再套一层 RAG。

RAG 解决的是如何根据问题找到相关信息。

主动性 Agent 还需要理解：

  • 人：用户是谁，承担什么职责，有什么目标。
  • 事：当前有哪些工作事项，进展如何，有什么风险。
  • 关系：人与人、人与项目、事项与事项之间有什么关系。
  • 时间：事情什么时候发生，什么时候应该完成，当前处于什么阶段。
  • 权限：谁可以看到什么，谁可以执行什么。
  • 结果：之前的行动产生了什么结果，用户有什么反馈。

这些信息必须持续编译、更新、关联和验证。

我们把这个过程称为 Context Compiler（CC）。

这台编译器怎么设计，我在 从程序编译器到企业上下文编译器 里完整展开过，这篇只谈它和主动性的关系。

CC 的目标不是建立一个更大的知识库，而是把分散的工作信息编译为 Agent 可以理解和使用的个人与企业上下文。

四、从信息流到工作理解：Context Compiler

在我们的实践中，CC 是一个非常重要的基础设施。

企业中的信息分散在聊天、群聊、会议、文档、审批、日历和各种业务系统中。

这些数据本身并不等于知识，更不等于可以直接用于主动决策的上下文。

CC 需要持续完成几个过程：

第一，采集和理解信息。

从不同数据源提取工作事实、事件、人物、项目、决策和事项。

第二，建立关联。

把人、事、组织、项目、文档和时间连接起来，理解它们之间的关系。

第三，形成工作事项台账。

不仅记录一条任务，还要理解任务的负责人、参与人、优先级、截止时间、依赖、状态和来源。

这本台账的个人版我实际跑过：每天 1000 条钉钉消息，我让一个 Agent 先编译再开口 里的结论是，主动性不是模型的能力，是编译的副产品。

第四，持续校正。

区分事实和推断，保留信息来源，根据新信息更新状态，通过用户反馈修正错误。

第五，建立权限边界。

上下文的可见性和使用范围必须继承原始数据的权限，不能因为经过 AI 编译就突破原来的访问边界。

这样，Agent 才不再只是面对一堆等待检索的文档，而是拥有一个持续更新的工作世界模型。

五、主动性 Agent 的三个核心能力

我倾向于把真正的主动性分成三个阶段。

1. 自主发现：发现值得做的事情

Agent 应该持续理解工作上下文，而不是等待用户提出问题。

发现的对象可以是：

  • 尚未被明确创建的工作事项。
  • 可能影响目标的风险。
  • 长期没有进展的阻塞。
  • 需要某个人做出的决策。
  • 可以提前完成的准备工作。
  • 值得主动发起的协作。
  • 可以由 AI 直接完成的工作。

这里需要强调：事件和定时扫描只是发现机制的输入，不是发现能力本身。

2. 自主判断：决定谁、何时、做什么

发现一件事情，并不意味着一定要打扰用户。

Agent 必须判断：

  • 事情是否真实存在？
  • 是否值得现在处理？
  • 对谁最重要？
  • 谁最适合承担责任？
  • 用户是否已经知道或正在处理？
  • 现在触达是否合适？
  • AI 是否具备足够的依据提出建议？

这是一个多目标决策问题。

错误的推荐不仅没有价值，还会消耗用户对 Agent 的信任。

3. 主动推进：让事情真正完成

推荐只是开始，不是终点。

Agent 应该能够：

  • 向正确的人解释问题。
  • 提出明确的下一步行动。
  • 在获得授权后调用工具执行。
  • 跟踪任务和协作进展。
  • 识别新的阻塞。
  • 根据执行结果继续调整。

这使 Agent 从一个信息助手，逐渐变成真正参与工作过程的数字员工。

六、主动性不意味着无限自主

这里有一个必须认真处理的问题。

主动发现和自主执行是两件不同的事情。

我认为应该明确区分四种行为：

  1. 观察：理解环境、信息和工作变化。
  2. 推荐：判断值得做什么，并向用户解释原因。
  3. 授权：明确执行范围、影响和责任。
  4. 执行：在允许的权限范围内完成任务。

低风险、可撤销、用户已经明确授权的操作，可以自动执行。

但涉及对外沟通、组织承诺、重要审批和高影响数据变更的行为，应当有明确的人工确认机制。

真正成熟的 Agent，不是能够做所有事情，而是知道自己什么时候可以做、什么时候应该建议、什么时候必须等待人来决定。

七、主动性 Agent 的评价标准也需要改变

如果我们仍然用传统 AI 产品的 DAU、对话次数、工具调用次数、推送打开率衡量主动性，很容易走错方向。

主动性 Agent 应该有自己的评价体系。

我认为至少需要关注：

  • Discovery Recall：真正值得做的事情，有多少被发现？
  • Decision Precision：主动推荐中，有多少确实值得做？
  • Right Person Accuracy：是否找到了正确的人？
  • Timing Precision：是否选择了恰当的时机？
  • Action Conversion：推荐有多少转化为实际行动？
  • Outcome Rate：最终有多少推动了真实工作结果？
  • Disturbance Rate：有多少推荐造成了不必要的打扰？

特别要注意，不能只追求发现率和触达率。

一个每天给用户推荐几十条事项的 Agent，可能比一个每天只推荐一件真正重要的事情的 Agent 差得多。

主动性不是更积极地打扰用户，而是更准确地创造价值。

节制的这一半，我在 数字员工的活人感，一半是知道什么时候闭嘴 里专门写过：没有节制的主动性，比没有主动性更糟。

八、我们的实践：千问小钉

我们正在尝试把这些理念应用到企业工作场景。

千问小钉的定位不是普通聊天机器人，也不是一个定时执行任务的 Agent。

它希望成为企业工作场景的个性化推荐引擎。

它持续理解钉钉上的工作信息，编译个人与企业上下文，理解每个人的工作目标、职责、协作关系和工作事项。

然后，在这个基础上发现值得做的事情，找到合适的人，选择合适的时机，推荐行动，并调用千问办公完成任务。

整体体系由四部分组成：

  • 钉钉：工作信息、沟通协作和事件入口。
  • CC：持续编译个人与企业上下文。
  • EC：承载企业知识、业务关系和权限。
  • 千问小钉与千问办公：负责主动决策、推荐和任务执行。

最终形成一个闭环：

理解工作 → 发现事情 → 判断行动 → 找到人 → 主动推荐 → 授权执行 → 结果反馈 → 持续学习。

这里最重要的不是让 Agent 每天运行多少次，而是让它持续理解工作世界，并能够在没有明确指令的情况下发现真正值得做的事情。

九、Agent 的下一阶段竞争力

我认为，未来 Agent 的竞争力会逐渐发生变化。

第一阶段，比谁更聪明，谁能更好地理解自然语言。

第二阶段，比谁能调用更多工具，谁能更可靠地执行复杂任务。

第三阶段，比谁拥有更好的上下文，谁能真正理解用户和环境。

第四阶段，比谁更有主动性，谁能自主发现问题、识别机会、找到正确的人，并推动事情产生结果。

工具调用能力会逐渐成为基础设施。

上下文理解和主动决策能力，才可能形成长期差异化。

未来真正有价值的 Agent，不应该只是等待人类分配任务。

它应该能够理解目标，理解环境，发现尚未被提出的问题，并主动推动工作向前发展。

从自动执行，到自主发现；从人找 AI，到事找人。

这可能是 Agent 从工具走向数字员工的关键一步。
